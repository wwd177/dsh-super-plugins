# 多成员成果进入最终项目

子任务 `accepted` 仅表示这一版本登记产物（或增量补丁）被调用方接受。最终交付还须落在用户实际要使用的项目、文件或应用入口中。复用现有依赖任务或 `git-worktree` 合并流水线组织集成，不要求新增状态或所有项目都有相同测试命令。

## 路径 A：`git-worktree` 团队（推荐用于本地 Git 仓库）

1. 建队时通过 `workspaceMode: "git-worktree"` 与本地 `repoPath`（工具参数或侧栏「新建团队」表单均可）锁定 `baseCommit`，每个任务在独立 detached worktree 中按 `writeScopes` 协作，验收时自动生成经 SHA-256 校验的 `changes.patch`。
2. 全部相关任务验收后，先执行 `engine_team({action:"merge_preview", teamId})`（或点击工作台「预览 Git 合并」），在临时 detached staging worktree 中按拓扑顺序重放所有已验收补丁，检查是否有合并冲突并审查 `diffStat` 与变更文件清单（**不修改用户活工作树或任何现有分支**）。
3. 预览无冲突后，执行 `engine_team({action:"merge_apply", teamId, branchName?, integrationCheck?})`（或点击工作台「原子发布到新分支」）：可选在 `.git`-free 导出目录上运行最终集成 `integrationCheck`（`node_test` 或 `command_test`），全部通过后以原子 create-only 方式发布全新 `refs/heads/superagent/<slug>` 分支；也可导出交付 ZIP，依据包内 `HANDOFF.md` 与 `artifacts/<taskId>/changes.patch` 手工审查后合入主分支。
4. 用户确认后再将 `superagent/<slug>` 合并或 cherry-pick 到目标分支，并在目标仓库真实入口完成最终行为验收。

## 路径 B：隔离目录团队（非 Git 项目或手工合入）

1. 开工前明确唯一集成负责人、目标目录、受影响文件和起始版本。已有未提交修改也属于保留项；不要用全仓 reset、清理或强制覆盖获得“干净基线”。记录相关文件基线哈希或明确 Git 版本，写入前重核目标文件；不匹配则先处理冲突。
2. 将需要合入的子任务作为集成任务 `dependsOn`；先核对其检查、宿主异常接受理由与 `snapshotId`。集成读取引擎提供的固定版本依赖。下游副本可写，不能称为 OS 只读隔离。
3. 在隔离目录整理修改并做合适的构建/行为检查。按目标项目需要准备依赖，不复制秘密文件充当依赖。将改动精确应用到约定目标，保留他人修改；冲突时停在明确文件，不自动整仓回退。
4. 应用后必须在真实目标目录、最终版本重新检查实际行为。副本中通过的测试不能替代目标目录终检；无通用自动合并或失败自动还原承诺。必要的受信 `node_test` 应在派发前登记，并明确测试实际读取的目录与产物。
5. 保存交付证据：目标目录与基线、上游 `taskId`/`snapshotId`、实际改动文件、最终版本/哈希、目标目录检查命令及结果、未验项。检查覆盖不足时补行为案例或独立评审；非空断言、退出码、字段标签或哈希不能独自证明质量。

原件没有目标行为检查能力时，说明限制并完成可执行检查，不把“子任务全部通过”改写成“项目已交付”。简单或强耦合工作不为制造集成任务额外拆分。
